# 书架删除改为移到“最近删除”

状态：阶段 1 已实施；阶段 2 单文件试用已反馈，用户接受 Files 的“选择 → 恢复”入口以及未覆盖场景，trash 失败策略按用户决定统一为本批确认。阶段 0 已结束，C 线 iCloud 为环境缺口；既有工具栏间距测试失败已基线证实并单列于验证记录。本计划保留至 PR 合并时删除，现行规则见[首页与书架](../design/library.md)，后续安排见 [roadmap](../roadmap.md#书架交互待实施)。

## 目标

用户在书架删除文件或文件夹，内容进入系统“最近删除”，可在“文件”App 恢复。移到最近删除失败即按不支持处理，由用户本批确认永久删除或跳过，不静默降级。

## 改动前的代码风险与验证边界

- **删除在 actor 上同步执行。** `LibraryService.deleteLibraryItem`（`LibraryService.swift:559`）在 `ReaderService` actor 上同步做 `coordinatedWrite(.forDeleting)` + `removeItem`，再同步 `refreshLibraryShelf`。
- **可能死锁。** `CloudLibrary`（约 398–448 行）的工作线程持有文件协调，同时等待回到同一个 actor 提交结果。如果删除在 actor 上等这个协调，就构成锁环。这一点和 `trashItem` 本身会不会卡无关，必须先改掉。
- **批量队列只认冲突。** `LibraryModel` 用 `replacement` 暂停队列（110、386、423–460 行），确认后由 UIKit 先关掉弹窗再继续（`LibraryActions.swift:102–149`）。整套逻辑只认识“冲突替换”这一种暂停。
- **iCloud 被删项可能短暂闪回。** 扫描会用系统元数据快照补出磁盘上还没有的云端文件（`LibraryService.swift:362`），删除后旧快照可能让被删项短暂出现，系统元数据更新后自动消失。这是跟随文件系统的正常表现，应用不另做过滤（2026-10-14 用户决定）。
- **书签可能跟进废纸篓。** 书架用书签记住根目录，`resolveShelf` 会刷新过期书签（308 行），扫描一成功就会清掉 error（`bookshelf.rs:221`）。如果被删的文件夹里含有另一个书架的根目录，那个书架的书签可能跟着解析到废纸篓，继续把已删除的内容当作书架显示出来。
- **暂停导入不等于导入已停。** `pauseFileImports` 只发出取消信号，不等待工作结束（`ReaderService` 473–483 行）。
- **恢复后的书是新条目。** 扫描不计算 SHA；消失的行会被移除，恢复回来的文件变成新 ID、`book_id` 为空的新行，要到打开时才按 SHA 接回进度。用户已接受这一表现，不在扫描时计算 SHA。
- **“最近删除”的显示开关已经打开。** `Info.plist` 21–22 行已开启 `UIFileSharingEnabled` 与 `LSSupportsOpeningDocumentsInPlace`；本地 `Documents/.Trash` 能否出现在“文件”App 的“最近删除”里，仍要真机看。

## 阶段 0：调用方式试验

### 真机已得结论（2026-10-14，iOS 27.0.1，不再重复）

- 在协调写入（`.forDeleting`）里调用 `trashItem` 超过 10 秒未返回（本地 Documents，空闲时）；直接调用约 66 ms 成功。阶段 1 定为**直接调用**。
- 本地 Documents：直接调用后文件进入 `Documents/.Trash/`，在“文件”App 的“最近删除”里可见，但恢复报“无法完成此操作 / Nothing to process”，两次复现；文件仍留在 `.Trash`。没有具体修复思路前，不再重复本地恢复。
- 细节见[验证记录](../engineering/verification.md)。

### 模拟器结论（阶段 0 收尾）

- B 线（无 iCloud 模拟器，真实 App Documents）2/2 通过：TXT、文件夹直接调用 100–200 ms，进入 `Documents/.Trash/`，在“文件”App 最近删除可见。通过“更多 → 选择 → 选中 → 恢复”能回到原路径；**长按菜单的“恢复”在模拟器上也报 Nothing to process**。真机两次失败用的正是长按菜单，所以真机失败很可能是系统“文件”App 长按恢复的问题，而不是 `.Trash` 本身不能恢复。待阶段 2 真机用“选择 → 恢复”确认。
- 以文件夹为根的书签在删除后解析到 `.Trash/…`，恢复后解析回原路径，`stale=false`。阶段 1 第 5 步按“解析出的路径含 `.Trash` 一段”判断。
- C 线（已登录 iCloud 的模拟器）环境预检未通过：App 侧拿不到 iCloud 账户 token 和自身容器 URL，原因未定位（可执行文件已嵌入预期 entitlement）。记为环境缺口，iCloud 与外部目录在阶段 2 真机试用中确认。
- 试验代码丢弃不提交；证据在 `build/LibraryTrashProbe/`、`build/LibraryTrashSimulator/`，摘要见[验证记录](../engineering/verification.md)。

## 阶段 1：实现（一个 PR）

1. **删除改到 actor 之外执行。**
   - `trashItem`（以及用户确认后的永久删除 `removeItem`）放到独立队列执行，**直接调用，不放进协调写入**（阶段 0 真机证实嵌套会卡住）。
   - 安全作用域从删除前一直保持到 IO 完成，然后回到 actor 发布结果、重新校验状态。
   - 删除后的刷新用异步 `scanLibraryShelf`，不用同步的 `refreshLibraryShelf`，同时保留同等的“作废进行中扫描”的代数机制。
   - 非永久删除时，`trashItem` 的任何失败都映射为 `LibraryFileError.trashUnsupported`，不区分错误码，由用户本批确认永久删除或跳过；永久删除失败仍原样报告。
2. **区分“已删除”和“刷新失败”。**
   - 文件系统操作成功，就记为这一项已删除。
   - 之后的刷新失败只作为刷新错误报告，绝不把这一项当成未删除，再拿去重试永久删除。
3. **统一的批次暂停。**
   - 把 `replacement` 和“不支持最近删除”合并成一个待决定的枚举，复用 UIKit 先关弹窗再继续的机制，并更新所有原本只认 `replacement` 的暂停判断和忙碌标记。
   - 每一项都先尝试移到“最近删除”。只有这一项移到最近删除失败，才进入待决定；“同一书架”不能作为不支持的依据。
   - 本批只问一次。用户的选择（永久删除或跳过）适用于本批之后所有移到最近删除失败的项，批次结束即清空。
   - 文案要写明作用范围：“本批中有项目所在位置不支持最近删除，删除后无法恢复。”按钮：“永久删除这些项目 / 跳过”。
   - 本轮不做撤销。
4. **删除前取消正在进行的打开。** 被删路径（含文件夹的后代）如果正在打开，调用 `cancelOpening`。这一步只取消应用的打开准备，不保证系统下载已经停止，文档不要写成“已停止所有 IO”。暂停导入保持现状（只发出取消信号）。 本轮仅取消同 `shelfId` 且路径相同或按路径分段属于被删路径后代的打开；跨书架重叠根不做物理路径解析，文件被移走时沿用现有打开错误。
5. **书架根位于废纸篓时视为找不到。**
   - 书架解析书签后，如果根目录位于废纸篓（解析出的路径中含 `.Trash` 一段；阶段 0 已确认本地书签会解析到这里），就当作找不到，显示现有的“需要重新连接”，不扫描、不刷新书签。
   - 这个判断不需要额外状态，重启后自然成立；文件夹从“最近删除”恢复后，书签解析回原位置，书架自动恢复。
   - 不做删除前的嵌套书架检测，也不在确认框里提示（用户决定）。iCloud 与外部目录的废纸篓路径在阶段 2 确认，如有不同再补判断。
6. **文案**：首个确认框标题改为“移到最近删除？”；说明改为“可在‘文件’App 的‘最近删除’中恢复。书签和笔记会保留。”；按钮改为“移到最近删除”。三个入口（长按菜单、多选工具栏、列表左滑）共用这个确认框。
7. **文档**：同步修改[数据专题](../data/README.md)、[首页与书架](../design/library.md)、[同步设计](../data/sync.md)中“实际删除”的描述；完成后将 roadmap 第 1 项标为已实现并链接设计文档；本计划保留实现状态，PR 合并时删除。

## 测试

分三条线：

- **A 离线确定性测试（每次提交跑）**：单元/UI 测试，注入删除。覆盖批次暂停（trash 失败时问一次、本批沿用、批次结束清空、先关弹窗再继续）、非 3328 的 trash 错误也进入待决定、永久删除错误照常报告、删除成功但刷新失败不重试永久删除、书架根位于废纸篓时显示“需要重新连接”、云端交接与删除并发不死锁、恢复后重新打开按 SHA 接回。更新 `testBookshelfSelectionDeletesOnlySelectedFiles` 的确认文案。
- **B 模拟器系统集成（本地 Mac，按需跑）**：真实 App Documents 加“文件”App 和选择器，见阶段 0。
- **C 已登录 iCloud 的模拟器（可选，串行，不进每次提交）**：自身容器与外部 iCloud Drive 的 TXT/文件夹；有限轮询等待同步，可用第二个模拟器或 Mac 观察跨端同步。

GitHub CI 仍只跑 Linux；iOS 测试在本地 Mac 跑，不跑全量。

## 阶段 2：用户真机集中试用（一次）

实现完成、A/B（及可用时的 C）通过后，交付一个正常构建，预先准备好各位置的一次性测试文件组。用户一次性完成：

- 为每个外部测试文件夹选择一次；
- 在“文件”App 删除、恢复准备好的 TXT 和文件夹组（文件夹组顺带覆盖“内含其他书架”的情况）；
- 重新打开一本书，看进度和笔记是否接回。

之后由协调者自动检查日志。真机才能确认的只有：iPhone 上实际的提供方、书签与沙盒行为，当前系统“文件”App 的恢复，以及真实 iCloud 的回收与性能。本地恢复如仍报 Nothing to process，记为未通过验收，不能以模拟器通过代替。没有第二台设备时，跨设备同步由 Mac 或模拟器观察，没法观察的列为缺口。

## 已确认的决定（2026-10-14）

- iCloud 被删项短暂闪回跟随系统，不另做过滤。
- 恢复的书先显示为新条目，打开后按 SHA 接回进度、书签与笔记。
- 嵌套书架用“书架根位于废纸篓即视为找不到”处理，不做删除前检测，确认框不提示。
- 测试以模拟器自动化为主，真机只做阶段 2 的一次集中试用。
